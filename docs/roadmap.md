# 進め方(ロードマップ)

『論理哲学論考』を Lean 4 で形式化するための作業の進め方の大枠。
何をどう形式化するか(範囲・表現・命名・検査の細部)は `docs/policy.md` が決める。両者が食い違ったら `policy.md` を正とする。

## 前提

- **本文の出典**はドイツ語原文(1921)と C. K. Ogden 英訳(1922)に限る。どちらも public domain
  - 日本語訳と Pears/McGuinness 英訳(1961)は著作権があるので使わない
  - Ogden 版に付いている Russell の序文は除く(Russell は 1970 年没で、日本では保護期間内)
- **本文は GitHub に上げない**:本文データ(`source/` の生成物)は git で管理せず、手元で再生成する。commit するファイル(Lean の docstring、対応記録など)にも本文を丸ごと・長く引用しない。解説の中の短い断片はよい(`source/README.md`)
- **言語**:Lean の実装(コード・docstring・識別子)は英語。ドキュメントは日本語
- **形式化は「モデル化」であって、論考そのものの再現ではない**。ずれを消すことより、ずれを記録して追跡できるようにすることを目標にする(`policy.md` §1)

後のフェーズで前の成果物の誤りが見つかったら、前の成果物を直す(特に、形式化中に見つかった読み違いは B の分類に戻す)。

| D | 方針を決める ★ | 完了 |

## 区切りの手順

フェーズ(A〜F)の区切りと、段階(`policy.md` §2 の 1〜4)の始めと終わりでは、次の4つを**必ず**行う。省略しない。

1. **機械的な検証**
   - `lake build` と `lake test` が通る。段階の締めくくりでは `lake test -- --strict`(その段階の未完成ゼロ)
   - 「機械で確かめられるのに、まだ検査していないこと」がないかを探す。あれば `lake test` に組み込み、わざと壊したデータでエラーになることを確かめる
2. **Claude 自身のレビュー**:その区切りまでの成果物と計画(`roadmap.md`、`policy.md`、分類、記録)を見直し、問題・食い違い・漏れを洗い出して直す
3. **ユーザーのレビュー**:段階の始めは分類のレビュー一覧(`lake exe render-review <段階>`)、終わりは対応記録と状態の一覧を見てもらう。了承を得るまで次に進まない
4. **記録**:結果をコミットし、何を確かめて何が見つかったかを報告に書く

## 整合性チェック(概要)

ほうっておくと、Lean のコードは論考から少しずつ離れていく。そこで、ずれを4つのレベルで捕まえる。実装方式は `policy.md` §6。

| レベル | 何を確かめるか | 方法 |
|---|---|---|
| 1 | 出典を追えるか:形式化した宣言に付けた命題番号が実在するか | `lake test` |
| 2 | 種別と宣言の種類が合っているか、余計な公理がないか。あわせて全命題の状態(形式化済み/未完成/この読みでは不成立/未着手/対象外)を一覧にする | `lake test` |
| 3 | 意味が合っているか:Lean の言明を日本語で読み直し、ずれを記録する | 対応記録(`correspondence/`)とブラインド逆翻訳 |
| 4 | モデルで確かめる:主張が矛盾しないこと、反例、論考内部の緊張関係 | Lean のモデル |
