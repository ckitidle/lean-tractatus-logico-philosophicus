# 進め方(ロードマップ)

『論理哲学論考』を Lean 4 で形式化するための作業の進め方。
何をどう形式化するか(範囲・表現・命名)はフェーズ D で `docs/policy.md` に決める。このファイルが決めるのは進め方だけ。

## 前提

- **本文の出典**はドイツ語原文(1921)と C. K. Ogden 英訳(1922)に限る。どちらも public domain。
  - 日本語訳と Pears/McGuinness 英訳(1961)は著作権があるので使わない
  - Ogden 版に付いている Russell の序文は除く(Russell は 1970 年没で、日本では保護期間内)
- **言語**:Lean の実装(コード・docstring・識別子)は英語。ドキュメントは日本語。原文はドイツ語・英語のまま引用する
- **形式化は「モデル化」であって、論考そのものの再現ではない**。論考は論理形式を「語りえず、示されるだけ」とする(4.12–4.1212)。Lean で書くこと自体が「語る」ことなので、これは論考の一つの読み方を形にしたものであり、ずれは必ず生じる。ずれを消すことより、**ずれを記録して追跡できるようにすること**を目標にする(下の「整合性チェック」)

## フェーズ

各フェーズは、成果物をリポジトリに置いてコミットしたら終わり。★のところでユーザーがレビューする。
後のフェーズで前の成果物の誤りが見つかったら、前の成果物を直す(特に F → B の読解ノート)。

### A. 本文を整備する

- 複数の版(Project Gutenberg #5740、Standard Ebooks、archive.org の 1922 年版)を突き合わせて、命題番号をキーにした構造化データ `source/` を作る
  - 1つの版だけだと OCR や転記の誤りに気づけない。版によって違う箇所は記録しておく
  - 記号(5.101 の真理表、6 の `[p̄, ξ̄, N(ξ̄)]` など)は崩さずに残す
- 機械チェック:番号の抜けや重複がないか、番号の親子関係(n.m は n への注釈)が成り立つか。親子関係には不規則なところがあるので、例外は列挙しておく
- **完了条件**:すべての命題がドイツ語と英語の対で揃い、チェックが通る

### B. 通読と分類 ★

- 節(1〜7)ごとに読解ノート `docs/reading/<節>.md` を作る。下読みは Claude が行い、ユーザーはレビューする
- 各命題に付けるもの:
  - **種別**:定義/主張(公理の候補)/帰結(定理の候補)/解明・比喩/形式化不能
  - **根拠**:なぜその種別にしたか。種別を付けること自体が解釈なので、根拠を書いて後から見直せるようにする
  - **確信度**と、**解釈が分かれる**かどうかの印
  - その命題が使う概念と、関係する他の命題
- 節を横断した成果物:概念の目録、命題同士の依存関係
- **完了条件**:すべての命題に種別が付き、節ごとにユーザーのレビューが済んでいる

### C. 解釈の分かれ目を確認する

- B で「解釈が分かれる」と印を付けた箇所だけ、二次文献で確かめる
  - 候補:2.061 の独立性、6.3751 の色の排除、5.5 以降の N 演算子(Fogelin・Geach・Soames・Cheung の論争)、5.53 以降の同一性、5.6 以降の独我論
  - 参考:存在論は Suszko(1968)と Wolniewicz(1982)、N 演算子は Rogers & Wehmeier(2012)
- どの解釈を採るか、またはいくつかの解釈を並べて持つかを、各論点に記録する

### D. 方針を決める ★

- `docs/policy.md` に次を決める:範囲、主張の表現の仕方、命名、整合性チェックの細部、Mathlib を入れるか
- Lean と論考のずれのうち、最初からわかっているものも書いておく
  - Lean は構成的な型理論で、論考は古典的な二値論理 → `Classical` や `Bool` をどう使うか
  - 論考は型理論を退ける(3.33 以降)
  - 論考は同一性の記号を消去しようとする(5.53 以降)

### E. パイロット

- 1つの範囲(たとえば 2.0x〜2.06 と 5.101)を実際に形式化して、方針と整合性チェックの仕組みが回るか確かめる。うまくいかなければ D に戻る
- Mathlib と lean-lsp-mcp はここで入れる
- 整合性チェックのレベル 1・2(下記)の仕組みもここで作る

### F. 本実装

- D で決めた範囲を段階的に広げる。範囲を1つ広げるたびに、整合性チェックの記録を更新する

## 整合性チェック(論考との突き合わせ)

ほうっておくと、Lean のコードは論考から少しずつ離れていく。そこで、ずれを4つのレベルで捕まえる。上のレベルほど機械的に検査する。

### レベル 1:出典を追えるか(機械・CI)

- 論考の命題を形式化した宣言には、命題番号を付ける。候補は独自の attribute(例:`@[tractatus "2.062"]`)
- CI で次を確認する
  - 付いている番号が `source/` に実在する
  - docstring に原文を引用しているなら、`source/` の本文と一字一句同じである
- カバレッジのレポートを生成する:命題ごとに「形式化した/対象外(理由付き)/未着手」

### レベル 2:種別と Lean の宣言の種類が合っているか(機械・CI)

- B の種別と Lean の宣言を照らし合わせる
  - 主張 → structure や class のフィールド、または仮定
  - 帰結 → `theorem`(`sorry` なしで証明済み)
  - 定義 → `def` や `structure`
- 公理の混入を防ぐ:`#print axioms` で、標準の3つ(`propext`、`Classical.choice`、`Quot.sound`)以外の公理に依存していないことを確認する。プロジェクト独自の `axiom` は禁止する
- Lean 上の依存関係(どの定理がどの主張を使うか)を出力して、B の依存関係とずれている箇所を人が見直す候補として挙げる

### レベル 3:意味が合っているか(人+Claude・記録)

- 形式化した命題ごとに、対応記録を作る(置き場所は D で決める)
  - 原文(ドイツ語・英語)
  - Lean の言明
  - **逆翻訳**:Lean の言明を自然言語で読み直したもの
  - ずれ:形式化で失われたもの、付け加わったもの
  - 採った解釈(C の記録へのリンク)
- 選択肢:原文を見せずに Lean の言明だけを逆翻訳させ、原文と比べる「ブラインド逆翻訳」。読み手の思い込みが入りにくい。別エージェントを使うので、やるかどうかはその都度決める

### レベル 4:モデルで確かめる(Lean)

- **無矛盾性**:主張を集めた structure に具体的なインスタンス(有限のモデル)を作り、仮定が矛盾しないことを示す
- **空虚でないこと**:定理が仮定の矛盾や自明さから成り立っているだけでないことを、モデルで確認する
- **論考が導けないとする命題の確認**:たとえば 2.062「一つの事態の成立から他の事態の成立・不成立は推論できない」は、反例となるモデルを作って示す
- **論考の中の緊張関係**:6.3751(色の排除)と要素命題の独立性のように、論考の内部でぶつかる箇所は、ぶつかることそのものを定理として示せるか試す

レベル 1・2 は E で仕組みを作り、レベル 3・4 は E で書式を決めて F で積み上げる。
