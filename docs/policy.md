# 形式化の方針(フェーズ D)

『論考』を Lean 4 でどう形式化するかを決める。根拠は `docs/reading/`(全命題の分類)と `docs/interpretation.md`(論点ごとの扱い)。
状態:**案**(2026-11-06、Claude が作成。ユーザーのレビュー待ち)。パイロット(フェーズ E)の結果で直す。

## 1. 位置づけ

- これは論考の**一つの読み方のモデル化**であって、論考の再現ではない
  - 論考は、論理形式は語りえず示されるだけだとし(4.12〜4.1212)、自分の命題も最後には無意味と認めるべき解明だとする(6.54)
  - Lean の言明はすべて**メタ言語での記述**であり、論考が「示されるだけ」とするものも「語って」しまう。このずれは消せない前提として受け入れる
- 目標は、ずれを消すことではなく、**どこがどうずれているかを追跡できる形で記録すること**(整合性チェック、§6)
- Lean の型理論は論考を記述するための道具である。論考が型理論を退けること(3.33〜3.333)と矛盾するとは考えないが、ずれとして記録する(§8)

## 2. 範囲と段階

## 3. 表現の設計

### 3.1 二つの層

- **意味論の層**(段階 1 から):命題を「それを真にする真理可能性の集合」として扱う。論理結合子はその上の演算として定義する。対象や名前としては扱わない(4.0312、5.4)
- **構文論の層**(段階 2 から):命題記号を、要素命題から真理操作(最終的には N)で作られる帰納的な型として定義し、意味論の層へ解釈する

### 3.2 基本の型(段階 1 のスケッチ)

```lean
-- 事態(要素命題が主張するもの)と対象は、正体に立ち入らずパラメータにする(5.557)
variable (Atom : Type*) (Object : Type*)

/-- 2.06: reality = which atomic facts exist and which do not (a truth-possibility, 4.3) -/
abbrev TruthPossibility := Atom → Bool

/-- 2.04: the world = the totality of existent atomic facts -/
abbrev World := Set Atom

/-- 4.2: the sense of a proposition = its agreement with truth-possibilities,
    represented by its truth-grounds (5.101) -/
abbrev Sense := Set (TruthPossibility Atom)

/-- logical space: the truth-possibilities that are possible at all -/
structure LogicalSpace where
  possible : Set (TruthPossibility Atom)

/-- 2.061 (claim): atomic facts are independent of one another -/
def Independent (L : LogicalSpace Atom) : Prop := L.possible = Set.univ
```

- 真理値は `Bool` を使う。有限の場合に数え上げ(`Fintype.card`)ができ、トートロジーの判定が計算できるため。`Prop` との行き来は Mathlib の補題に任せる
- 対象の形式(2.0141)は、事態から構成要素の対象への写像を持たせて「その対象が現れうる事態の集合」として定義する(`interpretation.md` の object_form)
- 世界(`Set Atom`)と現実(`Atom → Bool`)は別々に定義し、両者の対応を定理にする(2.063)

### 3.3 主張は仮定、公理は使わない

- 論考の主張(`claim`)は、**Prop を値とする定義**(上の `Independent` のような「モデルについての条件」)として書く。それを使う定理は仮定として受け取る:

  ```lean
  theorem no_inference_between_atomic_facts (L : LogicalSpace Atom) (h : Independent L) ... -- 2.062
  ```

- プロジェクト独自の `axiom` は**禁止**。主張を全て満たす具体的なモデルを作って、仮定が矛盾しないことを示す(§6 レベル 4)
- 主張が実は定義から証明できるとわかったら、`theorem` にして、`classification.tsv` の種別を `conseq` に直す

## 4. 種別と Lean の宣言の対応

| 種別(classification.tsv) | Lean の宣言 |
|---|---|
| `def` | `def` / `abbrev` / `structure` / `inductive`(値が Prop でないもの) |
| `notation` | 記法を実装する `def` / `inductive`(必要なら `notation` も) |
| `claim` | Prop を値とする `def`(モデルについての条件)。定理では仮定として使う |
| `conseq` | `theorem`(`sorry` なし) |
| `elucid` / `out` | 宣言を作らない。対応表に理由を残す |

一つの命題に複数の宣言が対応してよい(例:2.062 の定理と、その反例モデル)。

## 5. 命名と docstring

- 名前空間は `Tractatus`。識別子は内容を表す英語(例:`Tractatus.no_inference_between_atomic_facts`)。命題番号は名前に入れず、attribute で付ける(§6 レベル 1)
- 概念の名前は `docs/reading/README.md` の概念 ID に従う。Ogden 訳の訳語の揺れ(「state of affairs」が Sachlage と Sachverhalt の両方に使われるなど)を避けるため
- docstring には、その命題の Ogden 訳を `source/tractatus.json` の `text` から**一字一句そのまま**引用する。ドイツ語原文と食い違う箇所(4.1252 の式など)ではドイツ語も引用し、どちらに従ったかを書く
- docstring とコメントは英語(CLAUDE.md の取り決め)

## 6. 整合性チェックの実装方式

`docs/roadmap.md` の 4 つのレベルを、次のように実装する。レベル 1・2 の仕組みはフェーズ E で作る。

### レベル 1:出典を追えるか(CI)

- 独自の attribute `@[tlp "2.062"]` を `Tractatus/Meta.lean` に定義する。宣言と命題番号の対応を環境拡張に記録する
- 検査用の実行ファイル(仮称 `check-formalization`)が、ライブラリを読み込んで対応を取り出し、次を確認する
  - 付いている番号が `source/tractatus.json` に実在する
  - docstring の中の引用(書式を決めて抜き出す)が `text` と一字一句同じ
- カバレッジのレポート(命題ごとに「形式化した/対象外/未着手」)を `docs/coverage.md` に生成する。対象外の理由は `docs/reading/classification.tsv` の種別と §2 の一覧から引く

### レベル 2:種別と宣言の種類が合っているか(CI)

- 同じ実行ファイルが、attribute の付いた宣言の種類を §4 の表と照らし合わせる
- 公理の混入を防ぐ:attribute の付いた全ての定理について、依存する公理が `propext`、`Classical.choice`、`Quot.sound` だけであることを確認する(`#print axioms` と同じ情報を環境から集める)
- `sorry` を含む宣言があれば失敗させる

### レベル 3:意味が合っているか(記録)

- 段階ごとに `docs/correspondence/stage<N>.md` を作り、形式化した命題ごとに次を書く
  - 原文(英語、必要ならドイツ語)
  - Lean の言明(宣言名)
  - 逆翻訳:Lean の言明を日本語で読み直したもの
  - ずれ:形式化で失われたもの、付け加わったもの
  - 採った解釈(`docs/interpretation.md` の該当節)
- ブラインド逆翻訳(原文を見せずに逆翻訳させて比べる)は、`contested` の付いた命題についてだけ行う。別エージェントを使うので、やるときはユーザーに確認する

### レベル 4:モデルで確かめる(Lean)

- `Tractatus/Models/` に具体的なモデルを置く
  - 無矛盾性:段階ごとに、その段階で使う主張を全て満たすモデル
  - 反例:2.062 のような「推論できない」の反例、独立性が崩れるモデル(色の排除)
- 定理が空虚でないこと(仮定が矛盾していないこと)は、無矛盾性のモデルで同時に示される

## 7. Mathlib

- **入れる**。段階 1 から `Set`、`Finset`、`Fintype.card`、`Function` の補題、ブール代数を使う
- 入れるとき `lean-toolchain` を Mathlib の版に揃える(現在の v4.35.0 から変わる可能性がある)。`lake exe cache get` でビルド済みのキャッシュを取る
- 時期はフェーズ E の最初

## 8. 論考と Lean のずれ(既知のもの)

| ずれ | 論考 | このプロジェクト |
|---|---|---|
| 型理論 | 型理論を退ける(3.33〜3.333) | Lean の型をメタ言語の道具として使う |
| 論理 | 古典的な二値論理 | `Bool` と Mathlib の古典論理(`Classical`)を使う。構成的な証明にはこだわらない |
| 形式的概念 | 「対象がある」は無意味(4.1272) | `Nonempty Object` のように型についての命題を書ける。メタ言語での記述として許す |
| 論理定項 | 論理定項は何も代表しない(4.0312) | 意味論の層では結合子を集合演算として定義する。構文論の層では記号として持つが、意味は真理関数だけで決まる |
| 同一性 | 同一性の記号を消す(5.53) | 段階 4 まではメタ言語の等号(`=`)を自由に使う |
| 数 | 数は操作の指数(6.021) | Lean の `Nat` を使い、操作の反復回数との対応を定理にする |
| 語る/示す | 示されるものは語られえない(4.1212) | Lean の言明はすべて語っている。メタ定理として表せるものだけ表す |
