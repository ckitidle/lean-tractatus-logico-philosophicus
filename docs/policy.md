# 形式化の方針(フェーズ D)

『論考』を Lean 4 でどう形式化するかを決める。根拠は `analysis/reading/`(全命題の分類)と `analysis/interpretation.md`(論点ごとの扱い)。
状態:2026-11-06 に Claude が作成し、確認事項を §10 のとおり決めた。パイロット(フェーズ E)の結果で直す。

## 1. 位置づけ

- これは論考の**一つの読み方のモデル化**であって、論考の再現ではない
  - 論考は、論理形式は語りえず示されるだけだとし(4.12〜4.1212)、自分の命題も最後には無意味と認めるべき解明だとする(6.54)
  - Lean の言明はすべて**メタ言語での記述**であり、論考が「示されるだけ」とするものも「語って」しまう。このずれは消せない前提として受け入れる
- 目標は、ずれを消すことではなく、**どこがどうずれているかを追跡できる形で記録すること**(整合性チェック、§6)
- Lean の型理論は論考を記述するための道具である。論考が型理論を退けること(3.33〜3.333)と矛盾するとは考えないが、ずれとして記録する(§8)

## 1.5 ゴールと成果物

- 趣味のプロジェクト。**ゴールは段階 1〜3 と、段階 4 のうちできそうな 4a・4b を形式化すること**。4c・4d は重い・元の記述が形式的に曖昧なので「未着手(保留)」とし、理由を記録しておく(§2)
- 論考は原理的に全部を形式化できない本なので、**「全 526 命題について、形式化したか、なぜしなかったかが一つ残らず書いてある」ことを完全さの基準にする**。形式化した部分は Lean が証明を確かめる
- 成果物は次の3つ。公開用のページなどは作らない
  1. Lean のファイル(`Tractatus/`):論考の命題を定義と定理として書き、証明を Lean が機械的に確かめたもの
  2. 日本語の対応記録(`correspondence/`):命題ごとに、原文、Lean で何を言ったかの日本語での読み直し、論考とのずれ。Lean を読まずに中身を確かめるためのもの
  3. 下準備の資料:分析の結果(`analysis/`:分類、解釈、本文の突き合わせ)と方針(`docs/`)。本文データ(`source/`)は手元で再生成するもので、git には入れない
- 検査はローカルの `lake build` と `lake test` で行う。GitHub への push と CI は、バックアップや共有がしたくなったときに考える

## 3. 表現の設計

### 3.1 二つの層

- **意味論の層**(段階 1 から):命題を「それを真にする真理可能性の集合」として扱う。論理結合子はその上の演算として定義する。対象や名前としては扱わない(4.0312、5.4)
- **構文論の層**(段階 2 から):命題記号を、要素命題から真理操作(最終的には N)で作られる帰納的な型として定義し、意味論の層へ解釈する

### 3.2 基本の型(段階 1 のスケッチ)

```lean
-- 事態(要素命題が主張するもの)と対象は、正体に立ち入らずパラメータにする(5.557)
variable (Atom : Type*) (Object : Type*)

/-- 2.06: reality = which atomic facts exist and which do not (a truth-possibility, 4.3) -/
abbrev TruthPossibility := Atom → Bool

/-- 2.04: the world, as the set of atomic facts that obtain -/
abbrev World := Set Atom

/-- 4.2: the sense of a proposition = its agreement with truth-possibilities,
    represented by its truth-grounds (5.101) -/
abbrev Sense := Set (TruthPossibility Atom)

/-- logical space: the truth-possibilities that are possible at all -/
structure LogicalSpace where
  possible : Set (TruthPossibility Atom)

/-- 2.061 (claim): independence — every combination is possible -/
def Independent (L : LogicalSpace Atom) : Prop := L.possible = Set.univ
```

- 真理値は `Bool` を使う。有限の場合に数え上げ(`Fintype.card`)ができ、トートロジーの判定が計算できるため。`Prop` との行き来は Mathlib の補題に任せる
- 対象の形式(2.0141)は、事態から構成要素の対象への写像を持たせて「その対象が現れうる事態の集合」として定義する(`interpretation.md` の object_form)
- 世界(`Set Atom`)と現実(`Atom → Bool`)は別々に定義し、両者の対応を定理にする(2.063)

### 3.3 主張は仮定、公理は使わない

- 論考の主張(`claim`)は、**Prop を値とする定義**(上の `Independent` のような「モデルについての条件」)として書く。それを使う定理は仮定として受け取る:

  ```lean
  theorem no_inference_between_atomic_facts (L : LogicalSpace Atom) (h : Independent L) ... -- 2.062
  ```

- プロジェクト独自の `axiom` は**禁止**。主張を全て満たす具体的なモデルを作って、仮定が矛盾しないことを示す(§6 レベル 4)
- 主張が実は定義から証明できるとわかったら、`theorem` にして、`classification.tsv` の種別を `conseq` に直す

### 3.4 定義で決まる定理と、中身のある定理

意味論の層を先に作る設計には、**定理の多くが「そう定義したから成り立つ」だけになる**危険がある。たとえば、論理空間を「全ての割り当て」と定義すれば、2.062(事態から事態は推論できない)はほぼ定義から出てくる。これは形式化が論考を確かめたことにはならない。論考の読み方を定義に織り込んだだけである。

対策:

- 定理ごとに、その性格をレベル 3 の記録に書く
  - **定義の展開**:定義を開けばすぐ成り立つもの。中身は定義(=解釈)の側にあるので、記録では「どの定義にどんな読みを織り込んだか」を説明する
  - **中身あり**:定義から自明でない推論を要するもの(数え上げ、N 演算子の表現的完全性、色の排除と独立性の衝突、同一性の消去など)
- 各段階に、中身のある定理を必ず含める。パイロットでは 4.27(K_n=2^n)と 5.101(16 個)がそれに当たる
- 「全部証明できた」ことではなく、「どの読みのもとで何が言え、何が言えないか」をプロジェクトの成果とみなす

## 4. 種別と Lean の宣言の対応

| 種別(classification.tsv) | Lean の宣言 |
|---|---|
| `def` | `def` / `abbrev` / `structure` / `inductive`。「トートロジーである」のような述語の定義は Prop を値とする `def` になってよい |
| `notation` | 記法を実装する `def` / `inductive`(必要なら `notation` も) |
| `claim` | Prop を値とする `def`(モデルについての条件)。定理では仮定として使う |
| `conseq` | `theorem` |
| `elucid` / `out` | 宣言を作らない。状態の一覧に理由を残す |

一つの命題に複数の宣言が対応してよい(例:2.062 の定理と、その反例モデル)。検査(§6 レベル 2)は「表の種類の宣言が少なくとも一つある」ことを確かめる。それに加えて、その命題についての補助の定理やモデルに札を付けてよい(例:主張 2.061 に、それを満たすモデルの定理を付ける)。

命題番号の札には、その宣言が命題に対してどういう役割かも付ける:

- **形式化**(既定):その命題を定義・主張・定理として書いたもの
- **反証**:その命題が、私たちが置いた読み方のもとでは成り立たないことを示した定理(Wittgenstein が誤りだと断定するものではない)(例:色の命題を要素命題とすると独立性と衝突する)。「主張を外したモデルでは結論が導けない」ことを示す定理(2.062 の反例モデルなど)は反証ではない。結論の命題に通常の札(形式化)を付ける

## 5. 命名と docstring

- 名前空間は `Tractatus`。識別子は内容を表す英語(例:`Tractatus.no_inference_between_atomic_facts`)。命題番号は名前に入れず、attribute で付ける(§6 レベル 1)
- 概念の名前は `analysis/reading/README.md` の概念 ID に従う。Ogden 訳の訳語の揺れ(「state of affairs」が Sachlage と Sachverhalt の両方に使われるなど)を避けるため
- docstring には、Lean の言明が何を表すかを自分の言葉で書く。本文を**長く**引用しない(本文の全体を GitHub に上げない方針、`source/README.md`)。短い命題や一句の引用はよい。ドイツ語原文と英訳が食い違う箇所(4.1252 の式など)では、どちらに従ったかを書く
- 本文は、命題番号から手元の `source/tractatus.json` で引く
- 長い引用は `lake test` が検査する(本文と15語以上連続して一致する箇所があればエラー。`source/README.md`)
- docstring とコメントは英語(CLAUDE.md の取り決め)

## 6. 整合性チェックの実装方式

`docs/roadmap.md` の 4 つのレベルを、次のように実装する。

レベル 1・2 の仕組みと、状態の一覧(§6.1)、対応記録を読む用の版の生成は、フェーズ E(パイロット)で作る。形式化の中身より検査の仕組みが先に膨らまないよう、パイロットでは必要な分だけ作り、F で足す。

### 6.1 命題ごとの状態の一覧(lake test の出力)

`lake test` は、検査の結果と一緒に、**全 526 命題の状態**を出力する。端末には集計を、`out/coverage.md`(git 管理外)には全命題を1行ずつ書き出す。

| 状態 | 意味 | 判定 |
|---|---|---|
| **形式化済み** | Lean で書いて、証明も通った | 札の付いた宣言があり、`sorry` を含まない |
| **未完成** | 言明は書いたが、証明がまだ通っていない(技術的な失敗・途中) | 札の付いた宣言が `sorry`(Lean の「証明は後で」の印)を含む |
| **この読みでは不成立** | 私たちが置いた読み方のもとでは論考の主張が成り立たないことを、Lean で証明した(哲学的な発見)。見込みだけで証明していないものはここに入れない | 役割が「反証」の札の付いた定理がある |
| **未着手** | 形式化する予定だが、まだ手を付けていない。4c・4d は「保留」と添えて理由を出す | 札がなく、`stage` が `1`〜`3`、`4a`〜`4d` |

### 6.2 テストを失敗させる条件

- **失敗させる(エラーにする)のは、作り方の誤りだけ**
  - 存在しない命題番号の札が付いている
  - 札の付いた宣言の種類が、分類と §4 の対応に合わない(例:分類が「主張」の命題を `theorem` で書いた)
  - `stage` が `out` / `basis` の命題に札が付いている(分類か形式化のどちらかが誤り)
  - 標準の3つ(`propext`、`Classical.choice`、`Quot.sound`)以外の公理に依存している
- **「未完成」や「この読みでは不成立」があってもテストは通す**。これらは作業の状態や結果であって誤りではない。そうしないと、途中の状態をコミットできない
- **段階を締めくくるときだけ、厳しい検査(`--strict`)で「その段階の未完成ゼロ」を確かめる**

### レベル 1:出典を追えるか(lake test)

- 独自の attribute `@[tlp "2.062"]` と `@[tlp_refutes "6.3751"]` を `Tractatus/Meta.lean` に定義した。札1枚ごとに、`Tractatus.Meta.tags` の下に補助の定義(型 `Tractatus.Meta.Tag`。宣言名・命題番号・反証かどうか)を作って記録する
  - Lean の独自の拡張領域(環境拡張)に記録する方法は採らなかった。検査ツールの側でも Lean の初期化処理を再現する必要があり、壊れやすいため。補助の定義なら、ビルド済みのライブラリを読み込むだけで取り出せる
- `lake test` の実体 `tools/TlpTest.lean`(実行ファイル `tlp-test`)が、本文データと分類表の検査(`tools/CheckSource.lean`)を行ったあと、ビルド済みのライブラリを読み込んで札を集め、番号が分類表に実在するかを確かめる。先に `lake build` が要る

### レベル 2:種別と宣言の種類が合っているか(lake test)

- 同じ実行ファイルが、札の付いた宣言の種類を §4 の表と照らし合わせ、依存する公理を集め(`#print axioms` と同じ情報)、`sorry` の有無から状態を決める(§6.1、§6.2)
- 検査が誤りを捕まえることは、わざと誤りを入れたファイル(存在しない番号、種類の食い違い、対象外の命題への札、`sorry`、定義への反証の札、独自の公理)で確かめた(2026-11-06)

### レベル 3:意味が合っているか(記録)

- この記録は、**Lean を読まない人が、形式化が論考に忠実かを判断するための主な窓口**になる。Lean の記号を使わず、日本語だけで読めるように書く
- 段階ごとに `correspondence/stage<N>.md` を作り、形式化した命題ごとに次を書く
  - 命題番号(原文は書かない。原文は読む用の版で差し込む。短い引用はよい)
  - Lean の言明(宣言名)
  - 逆翻訳:Lean の言明を日本語で読み直したもの
  - ずれ:形式化で失われたもの、付け加わったもの

## 10. 決めたことと理由(2026-11-06)

案の段階で確認事項にしていた 5 点。ユーザーは Lean に詳しくないので、Claude が検討して決めた。

1. **範囲と段階分け**:像の理論を二つに分け、意味と真偽(2.2〜2.225)を段階 1 に入れた(§2)。像の理論は論考前半の柱なので早く扱いたい。一方、構造の部分は名前と対象の対応という道具が揃ってからでないと中身のある形にならない
2. **主張は仮定として受け取る**(§3.3)。理由:
   - 「Wittgenstein の主張 X が成り立つなら Y が成り立つ」という条件付きの定理になるので、何がどの主張に依存しているかが、定理の形そのものに残る
   - 公理として宣言すると、主張どうしが矛盾していた場合に何でも証明できてしまい、しかもそれに気づけない
   - 主張を外したモデルも作れるので、色の排除のように「主張が崩れたらどうなるか」も示せる
3. **出典の追跡は Lean の attribute で行う**(§6 レベル 1)。理由:
   - 命題番号が宣言そのものに結びつき、ファイルの書き方に左右されない
   - レベル 2 の検査(宣言の種類、依存する公理、`sorry` の有無)は Lean の内部の情報からしか取れないので、どのみち Lean 側の検査ツールが要る。外部スクリプトで Lean のファイルを読む方式では、これが確実にできない
   - 費用は Lean のメタプログラミングで百行程度のコード。Claude が書く
4. **Mathlib を入れる**(§7)。Mathlib は Lean の標準的な数学ライブラリで、集合・有限集合の数え上げ・ブール代数などが揃っている。入れなければこれらを自前で証明し直すことになる。費用と対策:
   - `lean-toolchain` が Mathlib の版に固定される。版は `lake-manifest.json` に記録され、上げるときは意図して上げる
   - ビルド済みのキャッシュの取得に数 GB のダウンロードが要る(初回と版を上げたときだけ)
5. **分類のレビューは段階ごとに、範囲を絞って行う**。526 行を今すぐ全部見る必要はない
   - 各段階に入るときに、その段階の範囲の命題、`contested` の付いた命題、確信度 `low` の命題をまとめたレビュー用の一覧を Claude が作る。ユーザーはそれを見る
   - `elucid` と `out` は、形式化できる内容が隠れていないかを一覧で流し見する程度でよい
   - 分類は哲学的な判断で、Lean の知識は要らない。むしろ Claude の読みの偏りを正す一番の機会なので、ユーザーが論考を自分で読んで気づいたことは何でも反映する
